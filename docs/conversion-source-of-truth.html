四、需要你拍板的 4 个决策

❓ Q1 — 源文件（秒传判定对象）的规范落点

现状源文件在 data/uploads，但存储抽象 IStorageProvider 的根是 data/files。收口后秒传检查必须经抽象，可抽象只认自己的根。源文件的「规范位置」定在哪？
➡️ 推荐：统一到 data/files。源文件规范位置 = filesDataPath 下的确定性路径，秒传检查经 IStorageProvider.exists(源逻辑路径)。data/uploads 仅作上传临时缓冲，落盘后归一到 data/files。语义最干净：一个存储抽象管所有文件，embedded/standalone 同构。

❓ Q2 — 「已转」判据改查哪里

现状是 data/exports/conversion-cache/ 按 nodeId-updatedAt-paramKey + mtime TTL 的本地缓存。#430 将建 conversion_task 表。
➡️ 推荐：查 conversion_task.succeeded。已转 = 该（源描述符+目标格式）有 succeeded 记录，命中则直接经存储抽象取产物。彻底废弃本地 conversionCacheDir + mtime TTL。理由：standalone 下「转换成功」是全局事实，不该是本机私有缓存；且任务表本就为「状态可视」而建，已转是状态的一种。

❓ Q3 — 产物路径 / 去重键用哪个维度

现状缓存 key 是 nodeId-updatedAt-paramKey；地图已定去重键是 content_hash + src_fmt + dst_fmt。收口后产物路径的 key 用哪个？
➡️ 推荐：content_hash + src_fmt + dst_fmt。产物路径 = 节点目录 + {content_hash}.{src}.{dst}，与地图「任务身份=内容派生」一致，同内容同格式天然去重/秒传命中，与用户身份解耦。（nodeId-updatedAt 维度丢弃：editor 保存会改 updatedAt 但 fileHash 不变，用它做 key 会导致缓存频繁失效。）

❓ Q4 — embedded 兼容代价：同步→异步 + 路径迁移

现状秒传/缓存是同步 existsSync、根在 data/uploads/data/exports；收口后 IStorageProvider.exists 是异步、根在 data/files。这会引入 async 化 + 路径迁移，需改所有调用点（含同步端点 files/fileisExist）。
➡️ 推荐：接受 async 化 + 路径归一。行为语义不变，但调用链变 async。理由：地图已定「一套无状态抽象」，为 embedded 保留同步快路径会引入分支、违背同构原则；async 化是服务化（standalone 走 HTTP）的必然代价，embedded 下本地 fs 的 async 延迟可忽略。
