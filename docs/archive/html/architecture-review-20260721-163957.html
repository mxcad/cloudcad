2026-07-21 · 基于最近 60 次提交的热点分析 · 共 5 个候选

5 个候选 2 个强推荐 词汇: 模块 · 接口 · 深度 · seam · 适配器

概览

本次审查基于深度模块原则：一个模块的接口应该比其实现小得多，为调用者提供杠杆，为维护者提供局部性。 以下候选模块违反了这一原则——它们要么是浅层的（接口几乎和实现一样复杂），要么是上帝模块（职责过多，没 seam）。 每个候选都通过了删除测试：删除它会将复杂性分散到各处，而非真正消除它。

强推荐

1. mxcadManager 上帝模块

2,612 行
88 个 import
10+ 职责

📁 涉及文件

  • packages/frontend/src/services/mxcadManager/index.ts
  • packages/frontend/src/services/mxcadManager/mxcadManagerCore.ts
  • packages/frontend/src/services/mxcadManager/mxcadCollaboration.ts
  • packages/frontend/src/pages/CADEditorDirect.tsx

⚠️ 问题

  • • 命令注册（Mx_Save, Mx_NewFile, openFile, exportFile 等）混在同一个文件中
  • • 模块级可变状态（pendingImages, projectPermsCache, navigateFunction 等 6+ 个）
  • • 模块级副作用（setupBeforeUnloadHandler 在引用时立即执行）
  • • 重复逻辑：handleNewFileCommand 同时存在于 index.ts 和 mxcadManagerCore.ts
  • • 删除测试：删除此文件意味着将命令注册、文件打开、保存、导出、导航逻辑散落到各处

✅ 解决方案

将每个命令（Save, NewFile, OpenFile, ExportPDF, ExportDWG, ExportDXF, SaveAs, SaveToCloud） 提取为独立的命令对象，每个实现一个 Command 接口： interface Command { execute(context: CommandContext): Promise<Result> } mxcadManager/index.ts 只保留注册表（CommandRegistry）， 将调用者与具体命令解耦。命令的 seam 在 CommandRegistry 的接口处——测试可以注册 mock 命令。

📈 收益

  • • 杠杆：调用者只需了解 CommandRegistry 的 2-3 个方法，而非 2000 行的实现
  • • 局部性：每个命令的变更隔离在自己的文件中，不影响其他命令
  • • 测试：每个命令可以独立单元测试；整个注册表可以通过 mock 命令测试
  • • 无模块级状态：命令上下文通过参数传递，而非模块级变量

2. BatchDownloadService 上帝服务

556 行
10 个 DI 依赖
5+ 职责

📁 涉及文件

  • packages/backend/src/batch-download/batch-download.service.ts
  • packages/backend/src/batch-download/batch-download.controller.ts
  • packages/backend/src/batch-download/conversion-runner.ts
  • packages/backend/src/batch-download/archive-writer.ts

⚠️ 问题

  • • 10 个 DI 依赖意味着严重违反单一职责——它做了太多事
  • • 同一服务中混合了：任务创建、权限检查、文件夹展开、进度追踪、SSE 流
  • • 删除测试：删除 BatchDownloadService 意味着将依赖分散到 controller、新的 folder-expander、progress-tracker、sse-manager 中
  • • ArchiveWriter 和 ConversionRunner 是好的深度模块——但它们没有被 BatchDownloadService 通过 seam 使用

✅ 解决方案

将 BatchDownloadService 拆分为 4 个独立的模块，每个通过接口协作：

  • • FolderExpander — 文件夹展开 + 节点收集
  • • ProgressTracker — 进度追踪 + 状态持久化
  • • SseManager — SSE 事件流管理
  • • BatchDownloadOrchestrator — 编排器，协调上述三者的流程

📈 收益

  • • 杠杆：编排器接口很小（~3 方法），调用者无需了解内部 4 个模块
  • • 局部性：文件夹展开逻辑的 bug 只需修改 FolderExpander
  • • 测试：每个模块可以独立测试；SSE 部分可以用虚拟 EventEmitter 测试
  • • 依赖注入减少：编排器只需要 3 个注入而非 10 个

3. 外部参照逻辑分散在两个控制器之间

跨模块边界
2 个控制器
重复的 preloading 逻辑

📁 涉及文件

  • packages/backend/src/mxcad/external-ref/external-ref.controller.ts
  • packages/backend/src/mxcad/external-ref/external-reference-update.service.ts (623 行)
  • packages/backend/src/mxcad/infra/mxcad-file-access.controller.ts
  • packages/backend/src/mxcad/external-ref/external-reference-handler.service.ts

⚠️ 问题

  • • 外部参照的文件访问在 mxcad/infra/ 控制器中处理，但上传/管理在 mxcad/external-ref/ 控制器中
  • • 相同的 seam 被两个模块切割：preloading JSON 的读取逻辑（checkExists, getExtRefDirName, getPreloadingFileName 等模式）在多个服务中重复
  • • 删除测试：删除 infra controller 中的 ext-ref 代码后，它们会在 external-ref controller 中重现
  • • 控制器内联了过多的业务逻辑（token 解析、文件验证、大小检查）
⚠️ ADR 参考：ADR-0002 要求 FileSystemController 直接注入子服务而非通过 Facade。类似地，外部参照控制器也应将业务逻辑提取到深层服务中。这并不矛盾——而是在遵循相同的模式。

✅ 解决方案

  • • 将两个控制器中的 ext-ref 相关逻辑合并到一个 ExternalRefModule（已有，但需要调整 seam）
  • • 提取 PreloadingFileService：专门处理 preloading JSON 的读写、存在性检查、路径解析
  • • 将 external-ref.controller.ts 中的验证逻辑提取到 ExtRefValidatorService
  • • MxcadFileAccessController 中的 ext-ref 端点委托给 ExtRefModule

📈 收益

  • • 局部性：所有外部参照逻辑在一个模块内，不再跨 infra/ 和 external-ref/ 分散
  • • 杠杆：PreloadingFileService 的小接口（readPreloading, writePreloading, checkExists）替换了 3 个服务中的重复代码
  • • 测试：PreloadingFileService 可以用 mock 文件系统测试；控制器变薄后更容易测试

  • • 已提取 helpers.ts 和 initMxCAD.ts，但它们太薄——辅助函数没有深度

  • • 将路由守卫/文件打开逻辑提取到 useFileOpenGuard hook
  • • 将拖放打开逻辑提取到 useDropOpen hook
  • • 将外部参照上传提取到现有 useExternalReferenceUpload hook
  • • CADEditorDirect 本身只做编排：调用 4-5 个 hooks，保持 JSX 薄

📈 收益

  • • 杠杆：每个 hook 可以被其他组件复用（例如导出按钮可以在工具栏复用）
  • • 局部性：导出逻辑的 bug 不会干扰文件打开逻辑
  • • 测试：每个 hook 可以单独测试；CADEditorDirect 作为薄编排层只需集成测试

5. CommonModule 残留服务

21 个服务残留
4 个已拆出
无域归属

📁 涉及文件

  • packages/backend/src/common/services/ (21 个服务)
  • packages/backend/src/permission/ (已拆出，但 PermissionService 仍在 common 中)
  • packages/backend/src/roles/ (RoleInheritanceService 仍在 common 中)
  • packages/backend/src/storage-management/ (已拆出)

⚠️ 问题

  • • 浅层模块：common/services/ 是一个"杂物间"——21 个服务没有域归属
  • • 违反局部性：PermissionService 的变更需要同时在 common/ 和 permission/ 中查找
  • • 删除测试：删除 common/services/ 不会丢失功能——只是强制将它们分配到正确的域模块
  • • 大服务仍留在 common：PermissionService (507 行), RoleInheritanceService (547 行)
  • • 虽然 NestJS 运行时不受影响，但对"这个服务属于哪个域"的认知负荷增加了
⚠️ ADR 参考：ADR-0002 已确立了"将逻辑放在域模块中"的模式。此候选只是 ADR-0002 未完成的工作——不是推翻它，而是完成它。ADR-0002 的约束条件（Controller 直接注入子服务）继续适用。

✅ 解决方案

  • • PermissionService → 移动到 src/permission/services/
  • • RoleInheritanceService → 移动到 src/roles/services/
  • • StorageCleanupService → 移动到 src/storage-management/services/
  • • 其他服务 → 归入 cache-architecture / conversion / etc.
  • • 纯基础设施（ConcurrencyManager, TreeTraversalService）可保留在 common 中

📈 收益

  • • 局部性：每个域模块拥有自己的服务，变更时不需要跨目录跳转
  • • 杠杆：新开发者只需看域模块的目录即可理解该域
  • • 测试友好：域模块自包含后，mock 和测试设置更局部化
  • • 低风险：纯粹的移动操作，不改变接口或行为

🏆 首选推荐

#1: mxcadManager 上帝模块 → 命令模式

为什么是首选：

  • 规模最大：2,612 行是 repo 中最大的手写文件，88 个 import 意味着最高的耦合度
  • 最阻碍测试：模块级副作用和可变状态使得任何自动测试都无法进行——当前 0 测试
  • 热点区域：CAD 编辑器是产品的核心价值所在，变更频繁
  • 明确的 seam：命令模式是经过时间验证的深化策略——CommandRegistry 接口小，测试收益大
  • 低风险递增路径：可以先提取一个命令（如 ExportPDF）作为试验，验证模式后再推广

执行步骤

  • 1. 定义 Command 接口 + CommandContext 类型
  • 2. 提取 ExportPDF 命令作为试点
  • 3. 提取 CommandRegistry 并注册试点命令
  • 4. 逐一迁移其他命令（Save, NewFile, OpenFile...）
  • 5. 删除模块级可变状态，改用 Context 参数
  • 6. 删除 mxcadManagerCore.ts 中的重复代码

预期收益

  • • 2,612 行 → 9 个文件 × ~200-300 行
  • • 88 imports → 每个命令约 5-15 imports
  • • 0 测试 → 每个命令可单元测试
  • • 模块级状态 → 零模块级可变状态
  • • 新命令只需 addCommand(name, new MyCommand())
次选推荐：BatchDownloadService（#2）—— 10 个 DI 依赖是强烈的"听诊器信号"，且拆分后 SSE 流可以独立演进。
