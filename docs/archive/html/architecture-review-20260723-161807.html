① FileSystemService：33 个方法的纯委托门面

后端 · 文件系统模块

Strong

涉及文件：

packages/backend/src/file-system/services/file-system.service.ts packages/backend/src/file-system/controllers/*.ts

Problem

FileSystemService 有 7 个构造器依赖、33 个公开方法、184 行——每个方法都是单行委托。它不添加任何业务逻辑、验证、转换或横切关注点。ADR-0002 已经移除了控制器对其的依赖，但外部消费者（library/、mxcad/、version-control/）仍然通过它调用底层服务。

现状：浅层门面

FileSystemController ──→ FileSystemService
library/ ──→ FileSystemService
mxcad/ ──→ FileSystemService
version-control/ ──→ FileSystemService
│ FileSystemService（33 个委托方法）
│ ├── .createProject() → projectCrudService.createProject()
│ ├── .getChildren() → fileTreeService.getChildren()
│ ├── .search() → searchService.search()
│ └── ...30 more
ProjectCrudService FileTreeService SearchService ...

深化后：删除门面

FileSystemController ──→ ProjectCrudService
library/ ──→ FileTreeService 等直接注入
mxcad/ ──→ 或通过 FileSystemFacade（仅保留跨子服务方法）
version-control/ ──→ 直接注入所需服务
│ ProjectCrudService FileTreeService SearchService
│ NodeCopyMoveService StorageInfoService ...

Solution

执行删除测试：如果删除 FileSystemService，复杂性不会消失——它已经在底层服务中。复杂性不会"重新分布到调用方"因为调用方已经在直接调用底层服务（控制器端已在 ADR-0002 中完成）。剩下的唯一原因是外部模块（library/、mxcad/）依赖它。

方案：将外部模块的注入改为直接注入底层服务。如果某些外部模块需要跨多个子服务的调用，创建一个小型 FileSystemFacade——但只保留确实需要聚合的方法（2-3 个），而不是 33 个。

Benefits

  • Leverage：测试直接调用子服务，不再需要 mock 一层无逻辑的中间层
  • Locality：子服务签名变更时只需修改直接使用者，不再需要同步更新门面
  • Depth：调用方学到的是子服务的真实接口，而不是 33 个转发方法的浅层

② 三个权限服务均无接口隔离

后端 · 权限 / 文件系统 / 角色模块

Strong

涉及文件：

permission/services/permission.service.ts roles/project-permission.service.ts file-system/file-permission/file-system-permission.service.ts common/interfaces/permission-store.interface.ts share/share.service.ts file-operations/node-trash.service.ts batch-download/batch-download.service.ts library/library.service.ts common/guards/permissions.guard.ts common/guards/require-project-permission.guard.ts

Problem

三个权限服务——PermissionService、ProjectPermissionService、FileSystemPermissionService——被 15+ 个文件、8+ 个模块作为具体类直接 import，没有接口解耦。share/、node-trash/、batch-download/、mxcad/ 等多个 Layer 2/3 模块直接耦合到彼此的 import 图。

讽刺的是，common/interfaces/permission-store.interface.ts 已经定义了 IPermissionStore 接口（7 个方法），并通过 IPERMISSION_STORE 令牌导出——但它仅在 roles/ 内部使用。这套模式已经验证可行，却没有推广。

Solution

遵循现有的 OSS/Pro/TOB 可替换模块模式（IAuthProvider 模式已验证），为三个权限服务分别定义接口 + DI 令牌：

// 参考：IAuthProvider 接口 + AUTH_PROVIDER 令牌模式
export const IPERMISSION_SERVICE = 'IPermissionService';
export interface IPermissionService { ... }

// PermissionModule 中注册
{ provide: IPERMISSION_SERVICE, useClass: PermissionService }

Benefits

  • Seam：创建一个真正的适配器 seam——TOB 客户可以通过自定义 PermissionService 替换 OSS 实现，而不影响调用方
  • Locality：权限逻辑变更只影响适配器实现，不影响 15+ 个消费者
  • Testability：测试通过 mock 接口而非具体类，测试设置从模块级 mock 降为单行 stub

③ BatchDownloadOrchestrator.processJob：171 行上帝方法

后端 · 批量下载模块

Strong

涉及文件：

batch-download/batch-download-orchestrator.ts（237 行） batch-download/batch-download.service.ts（8 个依赖）

Problem

processJob（第 43-214 行）是一个 171 行的单一方法，没有提取辅助函数。它混合了文件遍历、格式转换调度、计数器更新、ZIP 构建、错误跟踪、目录结构维护六个职责。所有状态通过可变局部变量（completedCount、errorCount、errors、convertedFiles、archiveEntries）手动传递，难以独立测试。SseManager 虽已提取（好！），但核心编排仍是一块巨石。

现状

processJob() {
// 1. 状态更新（5行）
// 2. 展开文件夹（8行）
// 3. 遍历文件（80行）
// ├── 检查中止
// ├── 查询节点
// ├── 4种格式处理
// ├── 转换调度
// ├── 计数器更新
// └── 错误追踪
// 4. 空目录（10行）
// 5. error.json（5行）
// 6. 创建ZIP（15行）
// 7. 状态完成（10行）
}

深化后

processJob() {
const ctx = new JobContext(jobId, controller);
if (!ctx.load()) return;
ctx.expandFolders();
for (const item of ctx.items) {
processItem(item, ctx); // 可单独测试
}
finalizeArchive(ctx); // 可单独测试
}
// 每个子步骤有明确的输入/输出
processItem(item, ctx) {
const formats = getFormats(item);
for (const fmt of formats) {
const result = tryConvert(item, fmt);
ctx.record(result);
}
}

Solution

引入 JobContext 作为显式编排上下文，封装计数器、中止信号和错误集合。将 processJob 的六个步骤提取为独立方法（expandFolder、processItem、tryConvert、addEmptyDirs、finalizeArchive），各方法通过 JobContext 通信。

ADR 兼容性：不冲突。BatchDownloadModule 是 Layer 3（业务编排），其内部深化不受 ADR-0007 限制。

Benefits

  • Locality：格式转换、文件遍历、错误处理分别集中在一个可单独修改的方法
  • Testability：tryConvert 返回 ConversionResult，测试只需构造 JobContext 并验证结果
  • Depth：调用方（BatchDownloadService）只需调用 orchestrator.processJob(id, ctrl)，内部复杂性消失

④ 两个上传服务共享 14+ 重复依赖签名

后端 · mxcad/upload 模块

Strong

涉及文件：

mxcad/upload/file-conversion-upload.service.ts（14 依赖） mxcad/upload/file-merge.service.ts（14 依赖）

Problem

两个服务具有几乎相同的构造器签名，各注入 14+ 个依赖。依赖集合几乎完全重叠：ConfigService、MxFileSystemService、FileTreeService、NodeTrashService、FileSystemNodeService、CacheManagerService、StorageManager、IVersionControl、FileConversionService、ExternalRefService、UploadUtilityService、ThumbnailGenerationService、IStorageService。这是"依赖重复"的典型案例——应提取共享上下文门面。

graph LR subgraph 现状 UPLOAD[FileConversionUploadService
14 deps] MERGE[FileMergeService
14 deps] UPLOAD --> FS1[FileTreeService] UPLOAD --> ST1[StorageManager] UPLOAD --> TC1[ThumbnailService] MERGE --> FS2[FileTreeService] MERGE --> ST2[StorageManager] MERGE --> TC2[ThumbnailService] end subgraph 深化后 CTX[UploadContext

Solution

提取 UploadContext（或 MxcadUploadFacade），将 14 个依赖收窄为 5-6 个高层方法。两个服务各注入 UploadContext + 各自独有的 2-3 个依赖。

@Injectable()
export class MxcadUploadFacade {
constructor(/* 14 deps hidden here */) {}
getNodeTree(nodeId) { ... }
validateAndSave(hash, buffer) { ... }
generateThumbnail(nodeId) { ... }
createVersion(nodeId, blob) { ... }
}

Benefits

  • Leverage：新增上传流程只需学习 UploadContext 的接口，而非注入 14 个服务
  • Locality：底层服务变更时只需修改 UploadContext 一处适配
  • Depth：大量文件系统/存储/缩略图行为隐藏在 5-6 个方法之后

⑤ AuthFacadeService：29 方法的门面无接口

后端 · 认证模块

Worth exploring

涉及文件：

auth/auth-facade.service.ts（525 行） auth/auth.controller.ts

Problem

AuthFacadeService 有 525 行、29 个公开方法，覆盖注册、登录、密码管理、邮箱/手机/微信绑定、Token 管理、资料检索。没有 IAuthFacade 接口，虽然其内部代理的 IAuthProvider 有接口定义。AuthFacadeService 本身是一个通过 authProvider 聚合多个子服务（RegistrationService、PasswordService、AccountBindingService、AuthTokenService、EmailVerificationService、SmsVerificationService、MembershipService）的门面。

删除测试：
如果删除 AuthFacadeService，其 29 个方法的逻辑不会消失——它们已经在各子服务中。AuthController 会直接注入 7 个子服务。接口不会简化，只是增加控制器的构造参数。这不是"删除后复杂性消失"的浅层门面——但缺少接口意味着测试需要 mock 具体类。

Solution

为 AuthFacadeService 提取 IAuthFacade 接口，遵循已建立的 IAuthProvider 模式。这不会改变 29 个方法的数量，但会创建一个清晰的 seam：

  • TOB 客户可以替换整个 AuthFacade（如果需要自定义编排逻辑）
  • 测试通过 IAuthFacade 接口 mock，避免加载整个 AuthModule
  • 接口作为文档——29 个方法的契约一目了然

Benefits

  • Seam：与 IAuthProvider 一致的 OSS/Pro/TOB 替换模式
  • Testability：AuthController 测试通过 mock IAuthFacade，无需加载 AuthModule
注意：29 个方法是 Auth 模块的合约大小——如果大多数方法都被控制器调用，这不是浅层问题。但缺少接口是未充分利用已有的模式（IAuthProvider、IPermissionStore）。

⑥ CacheWarmupService：声明的策略模式被具体类注入破坏

后端 · 缓存架构模块

Worth exploring

涉及文件：

cache-architecture/services/cache-warmup.service.ts

Problem

CacheWarmupService 的注释（第 58-67 行）声明"使用策略模式管理多种预热策略"，但构造函数注入的是具体类 HotDataStrategy、PermissionStrategy、RoleStrategy，而不是通过 IWarmupStrategy 接口令牌。注释与代码之间的差距意味着：

  • 无法在运行时或通过 DI 配置切换策略实现
  • 新增策略需要修改 CacheWarmupService 的构造函数（违反开闭原则）
  • 测试无法替换特定策略——必须 mock 整个服务

Solution

// 提取 IWarmupStrategy 接口
export const IWARMUP_STRATEGY = 'IWarmupStrategy';
export interface IWarmupStrategy {
readonly name: string;
warmup(): Promise<void>;
}

// 在 CacheArchitectureModule 中注册
{ provide: IWARMUP_STRATEGY, useClass: HotDataStrategy, multi: true },
{ provide: IWARMUP_STRATEGY, useClass: PermissionStrategy, multi: true },
{ provide: IWARMUP_STRATEGY, useClass: RoleStrategy, multi: true },

// CacheWarmupService 通过 @Inject(IWARMUP_STRATEGY) 接收策略列表

Benefits

  • Leverage：新增策略只需在模块注册 + 创建新类，零改动到 CacheWarmupService
  • Seam：DI 容器成了策略注册点，符合 NestJS 最佳实践
  • Locality：预热逻辑变更只影响单一策略类

⑦ LibraryController：13 个依赖的控制器过度注入

后端 · 资源库模块

Worth exploring

涉及文件：

library/library.controller.ts（13 依赖） library/library.service.ts

Problem

LibraryController 注入 13 个构造器依赖（第 103-120 行），包括 5 个来自 file-operations/ 的原始服务（NodeTrashService、NodeCopyMoveService、NodeUpdateService、ProjectCrudService）和 3 个来自 file-system/ 的服务。按照 NestJS 模式，控制器应很薄（只做路由委托），但 LibraryController 执行了大量的底层文件系统操作，暗示 LibraryService 未能提供足够深的接口封装这些操作。

⑧ IPermissionStore：好接口仅限模块内使用

后端 · 通用基础设施

Worth exploring

涉及文件：

common/interfaces/permission-store.interface.ts roles/providers/prisma-permission-store.ts roles/roles.module.ts

Problem

IPermissionStore 接口定义在 common/interfaces/ 中，通过 IPERMISSION_STORE DI 令牌导出（第 15 行），PrismaPermissionStore 是其实现。但所有外部消费者都直接导入 PermissionService（具体类），而 PermissionService 内部可能应该通过 IPermissionStore 委托——或者消费者直接使用该接口。

已定义的接口方法（7个）：
getPermissionByNames / getPermissionsByRole / getRoleWithPermissions /
getUserRoles / getRolesByUserIds / getUserSystemProjectRoles / assignSystemRole

Solution

有两种可能的深化方向（需进一步讨论决定）：

  1. PermissionService 实现 IPermissionStore：将 PrismaPermissionStore 合并到 PermissionService 中，对外暴露 IPermissionStore 接口
  2. 注入 IPermissionStore 到 PermissionService：PermissionService 成为注入 IPermissionStore 的门面，继承策略模式

Benefits

  • 利用已经存在的 seam，不需要创建新接口
  • 消费者通过接口解耦，与 IAuthProvider 模式对齐
