🧱 CloudCAD 架构深化回顾

基于 /codebase-design 词汇表的架构摩擦分析。每个候选项代表一个深化机会——将浅层模块重塑为深层模块，以提升可测试性和 AI 可导航性。

🏆 首要推荐

候选 #1 — 清理三个浅层委托服务

MxcadUploadService、MxcadConversionService、MxcadExternalRefService 三个服务 17 个方法中有 15 个是纯委托。每个委托测试覆盖的都是"委托被调用"而非"行为正确"。按删除测试：删除这些层会让复杂度集中到真正的实现中，而非分散。修复耗时最短、影响最大，是后续重构的基础。

Strong

#1 — 清理三个浅层委托服务 + 死代码 MxcadService

📁 涉及文件

  • packages/backend/src/mxcad/core/mxcad.service.ts — 空壳，11 行，无方法
  • packages/backend/src/mxcad/upload/mxcad-upload.service.ts — 5/5 委托 (154 行)
  • packages/backend/src/mxcad/conversion/mxcad-conversion.service.ts — 2/3 委托 (101 行)
  • packages/backend/src/mxcad/external-ref/mxcad-external-ref.service.ts — 7/7 委托 (95 行)
  • packages/backend/src/mxcad/interfaces/mxcad-upload.interface.ts
  • packages/backend/src/mxcad/interfaces/mxcad-conversion.interface.ts
  • packages/backend/src/mxcad/interfaces/mxcad-external-ref.interface.ts
  • packages/backend/src/mxcad/core/mxcad-core.module.ts — 注册了 4 个 useExisting 令牌

⚠️ 问题

  • • 三个服务共 15/17 个方法是纯委托，无任何业务逻辑
  • • 每个委托引入一个 NestJS DI 间接层，但无对应价值
  • • 测试验证的是"委托被调用"而非"行为正确"
  • • MxcadService 已完全无使用，属死代码

💡 解决方案

删除三个委托服务和空壳服务。控制器直接注入具体实现服务（FileConversionUploadService、FileConversionService、ExternalReferenceUpdateService 等）。移除对应的接口和令牌注册。测试改为针对具体实现。

🔴 当前 — 浅层

       └── MxcadUploadService          ← 5 个委托
            ├── FileConversionUploadService  ← 真实逻辑
            └── ChunkUploadManagerService    ← 真实逻辑

MxCadController
  └── @Inject(MXCAD_CONVERSION_SERVICE)
       └── MxcadConversionService      ← 3 个委托 + 1 个存根
            └── FileConversionService      ← 真实逻辑

MxCadController
  └── @Inject(MXCAD_EXTERNAL_REF_SERVICE)
       └── MxcadExternalRefService     ← 7 个委托
            ├── ExternalRefService           ← 真实逻辑
            └── ExternalReferenceUpdateService  ← 真实逻辑

🟢 深化后 — 深层

MxCadController
  └── @Inject(...) // 直接注入
       ├── FileConversionUploadService     ← 真实逻辑
       ├── ChunkUploadManagerService       ← 真实逻辑
       ├── FileConversionService           ← 真实逻辑
       ├── ExternalRefService              ← 真实逻辑
       └── ExternalReferenceUpdateService  ← 真实逻辑

📈 收益

  • • Locality：控制器直接调用实现，消除中间层
  • • Leverage：测试直接针对真实实现，而非委托
  • • 删除 3 个服务 + 1 个空壳 + 3 个接口 + 4 个令牌注册
  • • 移除了 checkTzStatus() 存根（可能隐藏 bug）

🔬 现在可测的测试

  • • FileConversionUploadService 的直接单元测试
  • • ExternalReferenceUpdateService 的直接单元测试
  • • 集成测试通过控制器注入真实服务

#2 — 拆分 MxCadController 中的版本历史逻辑

📁 涉及文件

  • packages/backend/src/mxcad/core/mxcad.controller.ts — 2369 行
  • packages/backend/src/mxcad/core/mxcad-request-context-builder.ts — 202 行

⚠️ 问题

  • • MxCadController 有 ~400 行内联版本历史逻辑（bin→mxweb 转换、MX 提交、临时文件管理、缓存）
  • • 控制器有 3 套不同的上下文构建逻辑：自身的 buildContextFromRequest() + validateTokenAndGetUserId() + checkFileAccessPermission()，均与 MxCadRequestContextBuilder 重复
  • • 控制器内联缓存管理（preloadingDataCache Map + cleanExpiredCache()）
  • • 14 个直接注入的依赖使测试难以隔离

💡 解决方案

提取 VersionHistoryService（封装 bin→mxweb 转换、MX 提交、临时文件清理）。控制器改用 MxCadRequestContextBuilder，删除重复方法。将缓存移至 CacheManagerService 或 @nestjs/cache-manager。

🔴 当前 — 浅层

MxCadController (2369 行, 14 个 DI)
├── 版本历史处理 (400 行内联)
│   ├── bin→mxweb 转换
│   ├── MX 提交
│   ├── 临时文件管理
│   └── caching
├── buildContextFromRequest()     ← 重复
├── validateTokenAndGetUserId()   ← 重复
├── checkFileAccessPermission()   ← 重复
├── preloadingDataCache Map       ← 内联
└── cleanExpiredCache()           ← 内联

MxCadRequestContextBuilder
├── buildContextFromRequest()     ← 相同逻辑
├── validateTokenAndGetUserId()   ← 相同逻辑
└── checkFileAccessPermission()   ← 相同逻辑

🟢 深化后 — 深层

MxCadController (瘦身后)
├── 委托 MxCadRequestContextBuilder
└── 委托 VersionHistoryService
    ├── bin→mxweb 转换
    ├── MX 提交
    ├── 临时文件管理
    └── 缓存 (通过 CacheManager)

MxCadRequestContextBuilder
└── 单一上下文构建来源

VersionHistoryService  ← 新深层模块
└── 所有版本逻辑在此

📈 收益

  • • Locality：版本历史逻辑集中在一个模块中
  • • Leverage：VersionHistoryService 的接口很小（2-3 个方法）
  • • 控制器行数减半，关注点清晰
  • • 消除与 MxCadRequestContextBuilder 的重复

🔬 现在可测的测试

  • • VersionHistoryService 的独立单元测试（mock 文件系统和转换）
  • • 控制器的逻辑简化后更易测试
Strong

#3 — 按操作域拆分 FileOperationsService

📁 涉及文件

  • packages/backend/src/file-operations/file-operations.service.ts — 1761 行
  • packages/backend/src/file-operations/project-crud.service.ts — 554 行
  • packages/backend/src/file-system/file-tree/file-tree.service.ts — 1240 行

⚠️ 问题

  • • FileOperationsService 处理 8 种不同操作域：删除、移动、复制、重命名、回收站、批量操作、存储清理、MX 集成
  • • 永久删除逻辑在 4 个方法中重复（deleteNode、permanentlyDeleteProject、permanentlyDeleteNode、permanentlyDeleteTrashItems）
  • • 树遍历模式重复：collectFilesToDelete（N+1 查询）、collectChildNodes（N+1）、getAllProjectNodeIds（CTE 单查询）
  • • 审计日志样板在 8 个方法中重复（手动 try/catch）

💡 解决方案

提取 NodeDeletionService、NodeMoveService、NodeCopyService、TrashService 四个领域服务。共享 TreeTraversalService（使用 CTE 单查询替代 N+1）。使用装饰器或 AOP 处理审计日志样板。每个新服务接口 2-3 个方法，深度显著增加。

🔴 当前 — 浅层

│   ├── 审计日志样板                   ← 重复
│   └── 缓存失效                       ← 重复
├── moveNode / batchMoveNodes
│   ├── collectChildNodes (N+1)        ← 重复模式
│   ├── 审计日志样板                   ← 重复
│   └── 缓存失效                       ← 重复
├── copyNode / batchCopyNodes
│   ├── 审计日志样板                   ← 重复
│   └── 缓存失效                       ← 重复
├── restoreNode / restoreTrashItems
│   ├── 审计日志样板                   ← 重复
│   └── 缓存失效                       ← 重复
├── clearTrash / clearProjectTrash
│   ├── 永久删除逻辑重复               ← 重复 4 次
│   └── 存储清理重复
└── permanentlyDeleteTrashItems
    └── 三步模式：收集→事务→清理      ← 重复 4 次

🟢 深化后 — 深层

TreeTraversalService         ← 共享深层模块
└── getNodeSubtree (CTE 单查询)
    ├── NodeDeletionService    ← 2 个方法
    │   └── 硬删除 / 软删除
    ├── NodeMoveService        ← 2 个方法

        └── 清空 / 恢复 / 永久删除

📈 收益

  • • Locality：每个操作域都有独立服务，修改不影响其他域
  • • Leverage：TreeTraversalService 替代 3 个重复遍历模式
  • • 路由级审计日志可通过 Guard/Interceptor 实现，而非手动
  • • 消除 ~200 行重复的永久删除逻辑

🔬 现在可测的测试

  • • TreeTraversalService 可独立测试遍历逻辑
  • • 每个领域服务可独立测试，mock 树遍历结果
  • • 集成测试验证完整操作链

#6 — 统一树遍历模式（CTE 替代 N+1）

📁 涉及文件

  • packages/backend/src/file-operations/file-operations.service.ts — collectFilesToDelete、collectChildNodes
  • packages/backend/src/file-system/file-tree/file-tree.service.ts — getAllProjectNodeIds（CTE）、getAllFilesUnderNode（N+1）

⚠️ 问题

  • • 树遍历在 3 个方法中实现，其中 2 个使用 N+1 查询（逐级 findMany）
  • • FileTreeService.getAllProjectNodeIds() 使用递归 CTE（单查询高效），但未被其他方法复用
  • • 每次添加新的树操作时，重复模式容易引入 bug

💡 解决方案

提取 TreeTraversalService，提供 getSubtreeIds(rootId)（CTE 单查询）、getSubtreeFiles(rootId)（仅文件节点）、getSubtreeFolders(rootId)（仅文件夹）。所有需要遍历操作的服务注入此服务。

📈 收益

  • • Leverage：一个接口替代 3 个重复模式
  • • 消除 N+1 查询，全部改用 CTE 单查询
  • • 性能提升：O(n) 查询 vs O(log n) 查询

🔬 现在可测的测试

  • • TreeTraversalService 独立测试（mock Prisma）
  • • 集成测试验证树结构查询正确性

#9 — 令牌注入接口采用不一致

📁 涉及文件

  • packages/backend/src/file-system/services/index.ts — 桶文件
  • packages/backend/src/file-system/interfaces/file-tree.interface.ts
  • packages/backend/src/file-system/interfaces/search.interface.ts
  • packages/backend/src/file-system/interfaces/storage-quota.interface.ts

⚠️ 问题

  • • IFILE_TREE_SERVICE 等接口令牌已定义，但采用不一致
  • • FileOperationsService 和 ProjectCrudService 通过令牌注入 FileTreeService
  • • NodeController、TrashController 等直接注入具体 FileTreeService
  • • 一半用令牌，一半用具体类，无统一模式

💡 解决方案

统一采用一种注入模式。由于当前只有一个适配器（Prisma），按 一个适配器意味着假设的接缝 原则，要么全部用具体类注入，要么确认第二个适配器需求后再引入令牌。

📈 收益

  • • 代码风格一致，降低认知负担
  • • 移除未使用的接口和桶导出

🔬 测试影响

  • • 所有消费者使用相同注入模式，测试设置统一
