1. MxCadService 薄门面

文件: packages/backend/src/mxcad/core/mxcad.service.ts

Worth exploring

问题

  • 32 个公开方法 — 接口几乎和实现一样复杂。浅模块的典型信号。
  • 大部分方法直接委托给子模块服务，自身不做知识浓缩。
  • 8 个 Prisma 直查方法（findNodeById, findUserById 等）重复了 DatabaseService 的能力，违反了"一个概念只在一个地方"原则。
  • 无 interface / seam — 所有消费者直接耦合到 @Injectable() 类，测试时必须导入整个模块。
  • 删除测试：删除 MxCadService 不会消除复杂度——复杂度会分散到各个调用方。但仍表明接口过大。

解决方案

  • 提取 Prisma 查询：将 8 个 find* 方法下沉到 FileSystemNodeService 或 DatabaseService，消除重复。
  • 引入 IMxCadService interface：定义真正的 seam，让子模块适配器驻留在 seam 之后。
  • 按聚合拆分：将"转换"、"保存"、"外部参照"、"上传"四个职责拆分为 4 个独立的深层模块，每个 5-8 个方法。
  • 门面只保留编排逻辑（例如 saveMxwebFile 中的乐观锁），其余透传由子模块直接暴露。

杠杆效应：1 个 seam 清洗 → N 个测试 + M 个调用方获得稳定性

2. mxcadManager 模块级状态

文件: packages/frontend/src/services/mxcadManager/index.ts (~2943 行)

Worth exploring

问题

  • 2943 行单体文件 — 同时包含：类定义（MxCADManager）、命令注册副作用、模块级状态变量、工具函数导出、类型导出。
  • 违反 AGENTS.md Zustand 单一数据源规则：documentModified、pendingImages、currentMxwebUrl、cachedPersonalSpaceId 是模块级变量而非 store 字段。
  • 命令注册（Mx_Save、exportFile 等）在模块评估时执行副作用——任何 import 行为都会触发，导致测试和 SSR 困难。
  • 删除测试：删除此模块时，其职责会扩散到 CADEditorDirect 和各个 hooks 中——模块确实在做有价值的事，但接口太乱。
  • 界面过于复杂：~20 个导出函数 + 类 + 类型 + 常量混在一个 barrel 中。

解决方案

  • 状态 → Zustand store：将 documentModified 合并到 useCADEditorStore，pendingImages 建立独立 usePendingImagesStore。
  • 命令注册后期化：将命令注册从模块评估时移到显式的 registerCommands() 调用，由 CADEditorDirect 在挂载时调用。
  • MxCADManager 类瘦身：将文件操作委托给子模块（已部分完成），只保留 CAD 引擎生命周期管理。
  • 按职责拆 barrel：类型 → mxcadTypes.ts，命令 → cmd/，引擎 → MxCADManager.ts。

杠杆效应：消除 5 个模块级变量 → 5 个测试可独立断言 + store selector 精确订阅

3. Storage 模块双接口债务

文件: packages/backend/src/storage/{storage.interface.ts, interfaces/storage-provider.interface.ts}

Strong

问题

  • 两个接口共存：storage.interface.ts（旧，5 方法）和 interfaces/storage-provider.interface.ts（新，13 方法），表明迁移未完成。
  • StorageService 虽然用新接口，但 getProvider() 暴露了底层 provider，打破了封装——调用方可以直接绕过抽象。
  • 被 6+ 模块 依赖，是耦合最广的基础模块。任何接口变化都会波及大量代码。
  • 无 barrel 导出——每个文件独立 import，调用方需要知道内部路径。

解决方案

  • 完成接口合并：删除旧接口，统一为新 13 方法接口。
  • 消除 getProvider()：所有 provider 级别操作（如 copyFromFs）提升到 StorageService 接口中，彻底隐藏 Provider 实现。
  • 添加 barrel：所有调用方统一从 @/storage 导入。
  • 清理命名：统一为 IStorageService，与 conversion 模块对齐。

杠杆效应：1 个 seam 清理 → 6+ 模块的依赖路径统一 → 测试 mock 成本降低

4. File-System 模块无 Seam

文件: packages/backend/src/file-system/ (60 文件, 9 子模块)

Strong

问题

  • 被 6 个外部模块 直接依赖，但所有服务都是 @Injectable() 类——零 interface。
  • 改变 FileTreeService 或 StorageQuotaService 的内部逻辑会传播到所有调用方，无法通过 seam 隔离变更。
  • 有 barrel 但只导出 8 个服务——没有任何契约定义。
  • 与 mxcad 模块形成循环依赖历史（之前已经解耦过一轮）。

解决方案

  • 为最依赖的 3 个服务引入接口：IFileTreeService、IStorageQuotaService、ISearchService。
  • 接口放置在 file-system/interfaces/，按 conversion 模块 的先例（每个接口 5-8 方法）。
  • 调用方改为 import interface token 而非直接 import 类。
  • 为集成测试提供 MemoryFileTreeAdapter。

杠杆效应：3 个 seam → 6 个依赖模块的解耦 + 集成测试可 mock 真实 seam

5. 前端测试基础设施未利用

文件: packages/frontend/src/test/ + packages/frontend/src/hooks/ + packages/frontend/src/stores/

Speculative

问题

  • 80+ 组件 + 36 hooks + 6 stores，仅 7 个测试套件。测试覆盖率极低。
  • MSW 基础设施 已经生成（自动从 Swagger 生成 handler），但只在 Playwright E2E 中使用，未用于 vitest 组件/hook 测试。
  • Store 测试为零——6 个 Zustand store 是纯逻辑（通过 getState/setState 可预测），极易测试但没测。
  • Hooks 测试为零——36 个 hooks 中的绝大多数可用 renderHook + MSW。
  • CI 中根本不跑 vitest（只有 type-check）。

解决方案

  • Store 测试先上：6 个 Zustand store 不需要 DOM、不需要 MSW——纯函数式断言。无借口不测试。
  • Hooks 测试利用 MSW：renderHook + wrapper + MSW handler 覆盖 useFileSystemData、useLibrary 等核心 hooks。
  • 关键组件快照：对 components/ui/ 的 26 个设计系统组件启动 Storybook 或 vitest 快照。
  • CI 开启 vitest：在 CI workflow 中添加 pnpm test 步骤。

杠杆效应：MSW 基础设施已就位（零成本）→ 测试 hooks 和 stores 可立即开始

首要推荐

先从 Storage 模块双接口合并（候选 3）开始。

  • 风险最低：已有清晰 seam（两个接口），只需选择其一、删除另一个。纯删除操作，不引入新抽象。
  • 回报最大：清理后 6+ 模块的依赖路径统一，消除 getProvider() 泄漏后集成测试可 mock seam 而非 mock 具体 provider。
  • followed by File-system seam 引入（候选 4），因为 6 个依赖模块中有 3 个同时依赖 storage 和 file-system，前者 seam 准备好了后者才能跟上。
