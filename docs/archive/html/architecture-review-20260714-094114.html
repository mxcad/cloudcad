CloudCAD 架构深化机会

基于 codebase-design 词汇表 · 模块 · 接口 · 深度 · 接缝 · 适配器 · 杠杆 · 局部性

2026-07-14
CloudCAD monorepo

概览

基于 100 条近期提交和全仓库扫描，识别出 6 个深化候选。 这些候选的共同主题是：间接层堆积（直通型 Façade）、 接缝渗漏（大控制器注入过多依赖）、 横切关注点纠缠（审计日志耦合在业务逻辑中）、 复制蔓延（5 处相同 SQL 模式、PC/Mobile 手动同步）。 每个候选都附有删除测试分析——如果删除该模块，复杂度是消失还是转移到调用方？

1. FileSystemService Façade — 纯直通层

Strong

📁 涉及文件

  • packages/backend/src/file-system/file-system.service.ts (176 行)
  • packages/backend/src/file-system/__tests__/file-system.service.spec.ts (190 行)
  • 消费者: library/, mxcad/, file-download/

🔍 删除测试

删除此服务后，复杂度不会消失——只是转移到调用方（他们需要直接注入 FileTreeService、FileOperationsService 和 ProjectCrudService）。该模块是纯中间人，零增值。

⚠️ 问题

25+ 个方法，每个都是纯委托。没有编排，没有转换，没有增值逻辑。接口与实现一样复杂——浅模块的典型案例。测试也全部是"验证委托给子服务"的模式。

✅ 解决方案

删除 FileSystemService。让消费者直接注入它们需要的子服务。如果将来需要在"文件系统"接缝处放置适配器（例如，用于测试的假文件树），直接在子服务接口处注入即可，不需要此中间层。

2. FileSystemController — 全能控制器

Strong

📁 涉及文件

  • packages/backend/src/file-system/file-system.controller.ts (1381 行)
  • packages/backend/src/file-system/dto/ (21 个 DTO 文件)
  • file-system.module.ts (导入 15 个模块)

🔍 删除测试

如果删除此控制器，其 10+ 个职责会均匀分散到路由层。复杂度不消失，只是换个地方——它本就应该从一开始就分开。

⚠️ 问题

单个控制器注入 11 个服务，处理10+ 个职责域（项目 CRUD、回收站、配额、成员、缩略图、下载、权限、搜索、路径解析）。downloadNodeWithFormat 方法独占 ~140 行。这个接口（URL 加参数）看似简单，但实现中耦合了大量不相关逻辑。

✅ 解决方案

按职责拆分为 4-5 个专用控制器：ProjectController、NodeController、TrashController、DownloadController、MemberController。每个控制器只注入相关服务，方法数从 ~35 缩到 ~8。

杠杆

每个小控制器的接口（路由 + DTO）只对应一个子域。测试只需 mock 相关服务，不必启动整个文件系统。

局部性

修改下载逻辑（ETag、流传输）不会影响项目 CRUD 或回收站。一个变更集中在 1 个文件中。

3. 模块循环依赖 — 4 处 forwardRef

Strong

📁 涉及文件

  • packages/backend/src/app.module.ts
  • packages/backend/src/auth/auth.module.ts
  • packages/backend/src/mxcad/mxcad.module.ts (named provider workaround)
  • packages/backend/src/file-system/file-system.module.ts

🔍 循环依赖链

  • AuthModule ↔ CommonModule (forwardRef)
  • AuthModule ↔ UsersModule (forwardRef)
  • MxCadModule ↔ FileSystemModule (forwardRef)
  • MxCadModule ↔ StorageModule (forwardRef)

⚠️ 问题

forwardRef 是 NestJS 解决循环依赖的逃逸阀，不是模块间关系的好设计。`MxCadModule` 中甚至出现了 Named Provider ('FileSystemServiceMain') 来绕过循环——这是典型的"用工具掩盖设计缺陷"。

注意：AuthModule 方向依赖已清理为单向，但前向引用仍在。

✅ 解决方案

提取共享内核模块：

  • 将 CommonModule 拆出 AuthCommonModule（仅含 Auth 需要的公共 Guard/Decorator）
  • 将 MxCadModule ↔ FileSystemModule 的交叉引用通过事件或共享接口解耦
  • 消除 'FileSystemServiceMain' named provider

杠杆

消除 forwardRef 后，模块可以独立加载、测试、mock。测试 Auth 不需要拉起 MxCad 的上下文。

局部性

模块依赖变成单向 DAG。修改 FileSystemModule 不会因循环引用导致 MxCadModule 意外变更。

4. AuthFacadeService — 审计日志与业务逻辑耦合

Worth exploring

📁 涉及文件

  • packages/backend/src/auth/auth-facade.service.ts (492 行)
  • packages/backend/src/auth/auth.module.ts

🔍 删除测试

删除审计日志后，每个方法仍保留业务逻辑——审计是横切关注点，不是核心价值。但 AuthFacadeService 本身不是纯直通，它做了有价值的编排。

⚠️ 问题

30+ 个方法的模式完全相同：调用子服务 → auditLogger.audit()。审计日志是横切关注点，混合编排层意味着测试编排时必须同时 mock 审计日志。

✅ 解决方案

使用 NestJS 自定义 装饰器 或 Interceptor 处理审计日志。@AuditLog('auth.register') 放在 Controller 方法上，将审计从编排层解耦。

📐 前后对比

现状
// 每个方法都需要mock审计
async register(dto, req) {
  const result = await this.provider.register(dto, req);
  await this.auditLogger.audit({...}); // ← 横切关注点
  return result;
}

async login(dto, req) {
  const result = await this.provider.login(dto, req);
  await this.auditLogger.audit({...}); // ← 重复
  return result;
}
// … 30+ 次相同模式
深化后
// Controller 层
@Post('register')
@AuditLog('auth.register') // ← 声明式
async register(...) { ... }

// Interceptor 自动处理
@Injectable()
class AuditInterceptor {
  intercept(context, next) {
    return next.handle().pipe(
      tap(() => this.auditLogger.audit({...}))
    );
  }
}

// 编排层不再 import AuditLogger
async register(dto, req) {
  return this.provider.register(dto, req);
}

杠杆

测试编排层不再需要 mock AuditLogger。新增操作自动获得审计能力，无需修改编排代码。审计策略可全局替换。

局部性

审计逻辑集中在 Interceptor 中一处修改。编排层只关注编排。

5. 全文搜索 + 树遍历重复模式

Worth exploring

📁 涉及文件

  • file-tree/file-tree.service.ts (FTS in 3 methods)
  • file-operations/project-crud.service.ts (FTS in 2 methods)
  • file-tree/file-tree.service.ts (getAllProjectNodeIds)
  • file-operations/file-operations.service.ts (getAllProjectNodeIds)

🔍 删除测试

如果抽取一个 SearchQueryBuilder 模块，FTS 不会消失，但会集中在一处。修改 FTS 行为（例如，切换到不同分词器）只需改 1 个文件而不是 5 个。

⚠️ 问题

5 处完全相同的 plainto_tsquery('simple', ...) + 降级到 ILIKE SQL 模式。getAllProjectNodeIds 的递归 CTE 在 2 个 service 中重复实现。修改搜索逻辑需要同步修改 5 个文件。

✅ 解决方案

提取 src/common/utils/search-query.builder.ts，封装 FTS 查询构建。将 getAllProjectNodeIds 归一到 FileTreeService，其他服务依赖它。

6. PC/Mobile 协同逻辑重复

Speculative

📁 涉及文件

  • frontend_mobile/src/composables/useCooperate.ts (186 行)
  • frontend/src/types/collaboration.ts
  • frontend_mobile/src/composables/useEditorState.ts (30 行)
  • frontend/src/stores/useCADEditorStore.ts (80 行)

⚠️ 注意

PC（React + Zustand）与 Mobile（Vue + Pinia）是不同的框架，共享代码不直接。但编码逻辑 (utf8ToBase64 / encodeV3WorkData) 是纯函数，完全可以提取到共享包。

⚠️ 问题

utf8ToBase64、base64ToUtf8、encodeV3WorkData、parseWorkData 等纯编码函数在 PC 和 Mobile 各实现一份。注释写着 "aligned with PC" 但两者可能 drift。

✅ 解决方案

将共享编码逻辑提取到 monorepo 的 packages/shared/（纯 TypeScript，零依赖）。PC 和 Mobile 都依赖此包。测试也只需一份。

🏆 首要推荐

从候选 #1 开始：删除 FileSystemService Façade。

  • → 最低风险：纯删除操作，不涉及逻辑变更。每个方法都是纯委托，删除后消费者行为不变。
  • → 立即收益：减少 1 个模块、176 行代码、190 行"假"测试。调用方更透明地了解其依赖。
  • → 解锁后续：移除 Façade 后，FileSystemController 的拆分会更自然——每个小控制器直接注入其需要的子服务，不再经过中间层。
  • → ADR 兼容：ADR-0002 要求 Controller 面向子服务而非 Façade——删除 Façade 实际上更符合 ADR 的原意。

删除测试结论：此 Façade 被删除后，复杂度不会消失——它均匀分布到调用方，但调用方本来就需要直接与其子服务交互。不存在"因集中管理而失去某能力"的风险。
