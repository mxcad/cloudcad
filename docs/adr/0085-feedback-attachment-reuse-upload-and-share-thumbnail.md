# 0085 — 反馈附件架构：复用图纸上传通道 + 通用截图器 + 附件资源管理（方案 B）

**Status**: accepted（2026-10-29）

## 背景

用户反馈机制一期已落地「提交→采纳→发会员奖励」闭环（匿名可提交、奖励不可匿名，见 feedback 模块）。二期支持反馈附件（截图/粘贴图片/上传附件/图纸文件），需求演进暴露三个架构决策：

1. **附件不止属于反馈**——头像、品牌 logo 等零散资源也需管理员统一管理；但「文件管理」命名会与文件系统（图纸树）/项目系统/个人空间概念冲突。
2. **图纸类附件可达 300MB**——若走通用附件上传，需新开大文件上传通道；而现有图纸上传已封装分片 + fileHash 秒传去重 + 转换缓存。
3. **图纸缩略图需要「打开图纸→渲染→截图」**——与「分享图纸生成分享图」是同一底层（前端 canvas 截图 `createCanvasImageData`，非后端 MxWebDwg2Jpg），可抽公共能力复用。

## 决策

### D1 附件资源管理：方案 B（非方案 A）

- **采纳方案 B**：反馈附件独立建模（`FeedbackAttachment`），管理员后台新增「**附件资源管理**」页聚合浏览/删除；**不采纳方案 A**（统一 `MediaAsset` 表 + 全部存量模块改造迁移）——头像/logo/图纸各有成型语义（绑定用户/品牌/图纸节点），强行统一破坏现有契约、违反「Surgical Changes」原则；聚合页 + 每类一个「列出/删除」适配器即可满足统一管理诉求。
- **术语铁律**：规范术语为「**附件资源（Attachment Resource）**」，指**不属于文件系统节点体系**的零散资源文件（反馈附件、头像、品牌 logo），无 nodeId/归属语义；**区别于文件系统节点（图纸树/项目/个人空间）**。「文件管理」「媒体资源」禁用；「附件」一词在外部参照语境是避讳词（CONTEXT.md 外部参照 `_避免_: 附件`），与「附件资源」是两个概念勿混。
- 附件资源管理页权限：整体 `SYSTEM_FEEDBACK_MANAGE`；头像/logo 删除额外要求 `SYSTEM_ADMIN`（不新增权限枚举，避免权限膨胀）。

### D2 图纸类附件复用现有图纸上传通道

- 图纸附件（mxweb/dwg/dxf）**不走通用附件上传**，复用现有 `POST mxcad/files/uploadFiles` + `fileisExist` 秒传预检（`ChunkUploadManagerService.uploadChunk` + `DrawingIngestService`）：分片上传、fileHash MD5 去重、转换产物缓存（`<hash>.<ext>.mxweb`，`cachedArtifactReady` 短路）全部现成，**无需新开大文件通道**（单请求 300MB 问题随之消失）。
- **两种存在形态**：
  - **实际文件副本**：上传的新图纸 copy 独立副本到附件存储（`filesDataPath/attachments/{YYYYMM}/{assetId}/`）——图纸 upload 产物是缓存（秒传/去重/可能被清），反馈证据需独立物理副本防缓存淘汰丢失。
  - **图纸引用**：用户引用自己项目/个人空间的已有图纸，**只存 `nodeId` 引用、不重复上传**；管理员可直接访问。
- **附件记录存 `nodeId` 作图纸引用**（唯一权威标识，可派生 path/缩略图/打开 URL）；`fileHash` 仅作次级去重标识。
- 反馈图纸上传默认**不落用户图纸空间**（`skipDb`/专用标记，避免污染用户图纸列表）；引用已有图纸不动原文件。

### D3 通用截图器（与分享图同源）

- 图纸类附件缩略图经「**打开图纸→渲染→截图**」通用截图器生成，与分享图同源——复用 `renderShareThumbnailInBackground`（`backgroundRender.ts`：安全守卫 + `openFile` + `generateThumbnail` + `uploadThumbnail`）+ ShareDialog 在屏快路径 + `pickThumbnailRegion`（框选区域）。分享图（指定区域/海报）与反馈附件共用同一截图器。
- **机制**：`CADEditorDirect` 全局底层叠加层 `visibility:hidden + zIndex:-1`（激活时 `Z_LAYERS.CAD_EDITOR=1000`），DOM 常驻保护 WebGL——图纸在底层渲染、反馈 UI 在上层，截图完成回反馈**不打断用户**。全图截图可后台静默；框选区域需临时把图纸带到可交互层（分享图「指定区域」同款：子页收起→常驻引擎框选→回弹预览）。
- 可截取**多张**、可**预览**截图。

### D4 上传通道与时机（图片/文档）

- 图片/文档附件走「**先上传拿 assetId → 反馈提交只带 assetIds 引用**」：独立上传端点 + 后端 `diskStorage` 落盘（不占内存），规避一次 multipart 耦合大文件；孤儿附件（上传超时未关联任何反馈）由清理任务兜底（默认 24h，可配置）。
- 匿名**可带附件**（匿名日限 3 条是主防线，附件同受类型/数量/大小限制）；匿名下载凭 code 查询响应带**短期签名 token**（约 10 分钟）；登录用 session；管理员用 `SYSTEM_FEEDBACK_READ`。
- 反馈撤回（CLOSED）**保留附件**供追溯；未来若支持删除反馈则级联删除附件。

### D5 配置、限额与安全

- 全部做成运行时配置 `feedback.*` 键（默认调大）：单文件上限（图纸/文档 300MB、图片单张 10MB）、数量（图片 20 / 图纸 5 / 文档 10 / 总 30）、内容长度。
- 服务端**魔数校验**（图片 jpg/png/webp/gif 校验头部字节，防伪造扩展名）+ 路径穿越防护（复用 `resolveWithinRoot`）+ 上传/删除**进审计**（新增 AuditAction）。

## 后果

- **主收益**：图纸类附件无需独立大文件上传通道，直接复用分片 + 秒传去重 + 转换缓存。
- **代价**：图纸产物缓存的存储 + 「copy 副本」的磁盘开销（反馈证据独立副本，防缓存淘汰）；附件资源管理为聚合视图，各模块（头像/logo）存储逻辑不动、只补列出/删除适配器。
- 缩略图生成依赖 `/cad-editor` 至少访问过一次（引擎已挂载）——与分享管理页同款前置约束，未挂载时无法凭空建引擎容器。
- 「积分/点数」方案明确不做（反馈奖励只在「采纳」事件上一次性发生，见 CONTEXT.md 反馈奖励），附件不改变奖励逻辑。
