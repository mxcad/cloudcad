# 0078 — `variant` 保持打包期概念，不下沉运行时

**Status**: accepted（2026-10-20）

`variant = private | oss` 保持 ADR-0075 定下的**打包期**语义，不为其构造任何运行时等价物。
运行时想知道「自己是私有部署」的需求（子票 T14）按**管理员手工开关**优雅降级，
而不是等一个运行时 variant。

## 背景

ADR-0075 把交付形态的判定顺序钉死为：**打包类型 → variant → 交付形态（裸机/Docker）→ 平台/构建通道**。
`variant` 全程是打包期菜单项，落进产物、不进入运行时配置。

`packages/backend/src/runtime-config/runtime-config.constants.ts` 的 69 个 key 里
**不存在** `variant`，也没有任何运行时配置能表达「当前产物是 private 还是 oss」。

子票 **T14（私有部署默认放开免费导出下载）** 的原始方案依赖一个前提：
*运行时能判断自己是私有变体，从而默认放行导出下载*。这个前提在当前架构下不成立。

于是出现一个真正的取舍：

- **造运行时等价物** = 把打包期决定运行时化。需要打通三处：打包脚本要写出这个值、
  config center 要能表达它、**增量升级包模型要能跨版本迁移它**。
- **不造** = T14 退化成「管理员手工开一个开关」，与现状（`freeExportDownload` 之类
  的单项 runtime config）无区别。

### 关键事实：private 包不对外交付

`private` 变体是公司内部私人包，不向任何公司或个人交付。因此：

- **不存在「交付后形态可变」的需求面**。买不到 private 包的人不可能提出
  「我想把它变成 OSS 包」。
- variant 在打包期就是**终局**——一个内部产物从生到死不改变它的形态归属。
- 运维侧无从切换 variant，也**不应**有这个能力：切换意味着在运行时改变一份
  产物的身份，而这份产物的身份决定它被允许做什么。

## 决策

### D1 不构造运行时 `variant`

不新增 `runtimeConfig.variant`、不新增环境变量、不在 config center 落这项。
打包期决定的事不进运行时。

### D2 T14 = 打包期按 variant 设不同**出厂默认值**，不是运行时开关

T14 的真身是「私有化部署包默认值断裂三件套」，其中最严重的是
`freeExportDownloadEnabled = false`：`restriction-engine.service.ts` 抛
`VipFeatureRequiredException` 403，前端弹「开通 VIP」引导，而**私有化部署包没有付费体系**
→ 用户永远无法开通 → 这是一条**死路**，不是「为安全考虑的限制」。

**修法是改出厂默认值，不是加开关**：

1. 给 `freeExportDownloadEnabled`（`runtime-config.constants.ts:845`）与
   `batchDownloadEnabled`（`:482`）补 `envKey`——两项当前都**没有** envKey，
   因此打包期目前无法按 variant 注入。
2. 打包/首次部署脚本按 variant 把值写进 `.env`：private 包写 `true`，oss 包写 `false`。

这一步**完全在 ADR-0078 的边界内**：variant 是打包期概念，它决定的正是
**出厂默认值**——不需要运行时知道自己是 private。`.env` 在 `resolveValue()` 里是
「部署期默认值层」，优先级低于 runtime：出厂值可以被管理员改，改了不会被覆盖。
这与「私有部署 = 内部环境、运维有完整权限」的定位一致。

**对比被否决的替代方案（运行时开关）**：管理员手工开一个开关是**绕过 bug 的 workaround**，
不是修 bug——出厂就带着一条走不通的死路，让运维自己去发现并开关，是把默认值写错的责任
转嫁给用户。

### D3 被拒的是「运行时自动感知形态」，不是「私有部署该默认放行」

区分两件事：

- **「私有部署默认放行导出」** —— 诉求成立，按 D2 用打包期默认值实现。
- **「运行时自动推断自己是私有部署」** —— 不成立，D1 拒绝。
  前者靠打包期决定出厂值，后者需要运行时知道形态归属。T14 只需要前者。

所以 T14 既不是「功能缩水」（出厂值会放开），也不是「运维手工开关」（不必手工）。


## 后果与代价

- **T14 的收益完整保留**：private 包出厂即放行导出下载，用户不会撞到「开通 VIP」死路。
  代价转移到**打包期**：打包脚本按 variant 写这两项的 `.env` 值，
  `freeExportDownloadEnabled` / `batchDownloadEnabled` 需补 `envKey`。
- **运行时与升级包模型零改动**（准确的边界）。对照 D1 的替代方案（运行时 variant）：
  要动运行时 + config center + 升级包模型三处，且增量升级包按 variant 出包
  （ADR-0075 的分期矩阵），「运行时可变 variant」会让升级包的 key 语义产生二义。
  本 ADR 只付**打包脚本一处**的改动。
- **一个未来读者会问的问题被写在这里**：
  「为什么 T14 不搞自动形态感知？」答案在 D3——前提不成立，而不是遗漏。
  这是本 ADR 存在的主要理由：一个**否定性决策**若无记录，
  下一个人接手 T14 或做形态相关需求时会自然重做一遍这个推导。
- **与 ADR-0077 形成对照，边界清晰**：
  - 交付**形态**（variant / 裸机 / Docker / 平台）→ 打包期定局，不进运行时、不进 schema
  - 运行**模式**（secure / normal）→ 运行时可变，走 runtime config 优先级链，不进 schema
  两者都不进 DDL，但原因不同：形态是产物的身份，模式是部署的策略。
