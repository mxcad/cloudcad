# 0078 — `variant` 保持打包期概念，不下沉运行时

**Status**: accepted（2026-10-20）

`variant = private | oss` 保持 ADR-0075 定下的**打包期**语义，不为其构造任何运行时等价物。
运行时想知道「自己是私有部署」的需求（子票 T14）按**管理员手工开关**优雅降级，
而不是等一个运行时 variant。

## 背景

ADR-0075 把交付形态的判定顺序钉死为：**打包类型 → variant → 交付形态（裸机/Docker）→ 平台/构建通道**。
`variant` 全程是打包期菜单项，落进产物、不进入运行时配置。

`packages/backend/src/runtime-config/runtime-config.constants.ts` 的 69 个 key 里
**不存在** `variant`，也没有任何运行时配置能表达「当前产物是 private 还是 oss」。

子票 **T14（私有部署默认放开免费导出下载）** 的原始方案依赖一个前提：
*运行时能判断自己是私有变体，从而默认放行导出下载*。这个前提在当前架构下不成立。

于是出现一个真正的取舍：

- **造运行时等价物** = 把打包期决定运行时化。需要打通三处：打包脚本要写出这个值、
  config center 要能表达它、**增量升级包模型要能跨版本迁移它**。
- **不造** = T14 退化成「管理员手工开一个开关」，与现状（`freeExportDownload` 之类
  的单项 runtime config）无区别。

### 关键事实：private 包不对外交付

`private` 变体是公司内部私人包，不向任何公司或个人交付。因此：

- **不存在「交付后形态可变」的需求面**。买不到 private 包的人不可能提出
  「我想把它变成 OSS 包」。
- variant 在打包期就是**终局**——一个内部产物从生到死不改变它的形态归属。
- 运维侧无从切换 variant，也**不应**有这个能力：切换意味着在运行时改变一份
  产物的身份，而这份产物的身份决定它被允许做什么。

## 决策

### D1 不构造运行时 `variant`

不新增 `runtimeConfig.variant`、不新增环境变量、不在 config center 落这项。
打包期决定的事不进运行时。

### D2 T14 降级为单项 runtime config 开关

T14 实现为「管理员手工开一个开关」——即普通意义上的 runtime config key，
走 ADR-0077 的既有优先级链，与普通/安全模式 profile 无关。

**默认值仍为关闭**（与现状一致）。私有部署的运维若需要放开，自行打开。
这与「私有部署 = 内部环境、运维有完整 shell 权限」的定位一致——
他们需要的是一个开关，不是一个自动推断的形态。

### D3 「私有部署该默认放行」这一诉求不成立

该诉求的前提是「运行时知道自己是私有部署」，而 D1 拒绝了这个前提。
所以 T14 不是「功能缩水」，而是**原本的需求就建立在错误前提上**：
私有部署需要放开导出，这个诉求可以成立（运维自己开开关即可），
但「系统自动知道自己是私有部署所以默认放开」这个自动化，前提不存在。

## 后果与代价

- **T14 的收益减半**：不再有「私有部署开箱即放行导出」的自动行为，
  首次部署后需运维手工开一次。接受——内部环境的运维有能力完成这一步，
  且这一步是**可见的、显式的**决策，而非静默的形态推断。
- **打包脚本、config center、升级包三处零改动**。这是本 ADR 最主要的收益。
  对照 D1 的替代方案：三处同步 + 增量升级包要处理「跨版本 variant 迁移」，
  而增量升级包按 variant 出包（ADR-0075 的分期矩阵），
  「运行时可变 variant」会让升级包的 key 语义产生二义。
- **一个未来读者会问的问题被写在这里**：
  「为什么 T14 不搞自动形态感知？」答案在 D3——前提不成立，而不是遗漏。
  这是本 ADR 存在的主要理由：一个**否定性决策**若无记录，
  下一个人接手 T14 或做形态相关需求时会自然重做一遍这个推导。
- **与 ADR-0077 形成对照，边界清晰**：
  - 交付**形态**（variant / 裸机 / Docker / 平台）→ 打包期定局，不进运行时、不进 schema
  - 运行**模式**（secure / normal）→ 运行时可变，走 runtime config 优先级链，不进 schema
  两者都不进 DDL，但原因不同：形态是产物的身份，模式是部署的策略。
