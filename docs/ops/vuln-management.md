## 1. 扫描范围

| 对象 | 方式 | 频率 | 责任人 |
|------|------|------|--------|
| 操作系统 / 中间件（PG、Redis、Nginx、Node） | 漏洞扫描工具 / 安全基线核查 | 每季度 | 安全管理员（SECURITY_ADMIN） |
| 应用镜像与依赖 | audit-ci CI 门禁 + `pnpm audit` 人工复核 | 每次 push/PR（门禁）+ 每月例行 | 系统管理员（SYSTEM_ADMIN） |
| Web 应用（OWASP Top 10） | DAST 工具 / 渗透测试 | 每年至少一次 | 安全管理员（SECURITY_ADMIN） |

（责任人列以角色名填实；各角色在岗人员见总单 CF-05 三员名单）

> **CI 依赖漏洞门禁与例行检查**（#423 联动）：`.github/workflows/ci.yml` 的 `dependency-scan` job 每次 push/PR 运行 `audit-ci --high`（生产依赖，秒级）。high+ 漏洞不在 allowlist（根目录 `audit-ci.json`）→ CI 立即变红 → 登记 issue 并 **48h 内处置**（门禁红比 §2 高危 7 天默认时限更严——门禁阻断合并，须当日响应；§2 仍为漏洞分级处置的默认时限）；**新增依赖引入的 high 漏洞禁止进 allowlist**（必须修复或回滚）。allowlist 条目 30 天复核：跟踪表 [`docs/ops/audit-ci-allowlist.md`](audit-ci-allowlist.md) 逐条核对复核截止日，能消即消（升级后从 allowlist 移除，git 历史即收缩台账），不能消的更新豁免理由与新截止日。

## 2. 漏洞分级与时限

| 等级（CVSS） | 处置时限 | 说明 |
|--------------|----------|------|
| 严重（≥9.0） | 48 小时内修复或缓解 | 可临时下线/封禁缓解 |
| 高危（7.0–8.9） | 7 天内 | — |
| 中危（4.0–6.9） | 30 天内，随版本迭代 | — |
| 低危（<4.0） | 下一常规版本 | 记录跟踪即可 |

（以上为制度默认时限，公司确认项见总单 CF-18）

## 3. 补丁管理流程

1. **跟踪**：订阅 OS 安全公告 / GitHub Advisory / 依赖机器人；
2. **评估**：确认影响面（是否涉及本部署的组件与版本），评估兼容性风险；
3. **测试**：补丁先在预发布环境验证核心链路（登录、图纸上传/打开/保存、协同）；
4. **实施**：按变更管理执行（备份先行，见 [backup-restore-policy.md](backup-restore-policy.md)），选择业务低峰窗口（默认 02:00–06:00，公司确认项见总单 CF-20）；
5. **验证**：升级后健康检查 + 抽样功能验证；
6. **记录**：登记至补丁台账。

## 5. 无法及时修复的处理

- 有缓解措施（WAF 规则、IP 封禁、关闭入口）的先缓解并记录；
- 无缓解措施的严重漏洞，上报应急总负责人（【待公司：CF-09 应急联系矩阵】）决定是否停服处置（走 [incident-response.md](incident-response.md) 流程）。
