Problem

两条 convertFile 分支逐段同构（路径解析 / 参数装配 / 平台分支 / 超时采信 / 输出解析 / 异常 salvage），逐字重复的片段至少 4 处；conversion-service 的 runner 又独立复刻了超时采信、输出解析、newpath 补齐。同一概念理解一次要读三个文件。

Solution

把「平台感知的参数序列化 + spawn/teardown + 超时与未启动分类 + 输出解析 + 失败分类 + newpath 补齐」合成一个 module，executeConversion 与 executeBinToMxweb 退化为薄调用方。engine-exec 已承担 spawn，本 module 承接其上的全部判定逻辑。

Wins

  • · locality：失败分类集中在一个 module
  • · 删除 250 行重复流程
  • · 平台分支 5 份 → 1 份
  • · newpath 补齐 8 处 → 1 处
  • · 超时采信竞态一处可测
  • · 两种部署模式结论一致
与 ADR-0069 的边界：契约文件 :15-17 明确把「路径绝对化/归一（各 adapter 的环境行为）」排除在纯函数契约之外。本 module 属 IO 层，不进 contracts（scan:purity 门禁会红灯），应落在 engine-exec 一侧或 backend 内 —— ADR-0069 的逃逸口第 4 条正是这个方向。另外 runner 与 backend 在 signal 分支的救回策略已出现真实差异（runner.ts:107-108 注释自述「与 backend 进程内路径一致」，但代码上 backend :445 合并了 exitCode==null 与 signal 两类而 runner 分开），这是收敛的直接收益。
跨模式行为分叉（收敛后可消除）：per-call timeout 在转发模式下被忽略 —— 进程内默认 180 s，转发走 PRIORITY_CONFIG[level].timeout，level 3 = 120 s；debugNodeId 在转发模式下被 pickContractFields 丢弃，saveConversionDebugInfo 永不执行。

Problem

写缓存的 mxcadUploadPath 默认非空（data/uploads），清理 cron 扫的是 batchConfig.conversionCacheDir（默认 data/exports/conversion-cache）—— 孤儿缓存永不被清扫。委托路径每次提交都真转，即使新鲜产物已在位。另有 3 种写入语义并存（copy / rename / rename 降级直传）。

Solution

把 key 派生（含 ext）、目录解析、新鲜度判断、写入、清理源全部收进一个 module，写方与清理由同一个目录出口取值；委托路径在提交前先过同一个命中判断。

Wins

  • · key 模板 7 → 1
  • · 目录错配缺陷消失
  • · 委托路径可命中缓存
  • · 写入语义 3 种 → 1 种
  • · 清理 cron 扫对目录
  • · 一个测试可锁死目录一致性
与 ADR-0060 §2 的冲突：ADR 声明「单文件与批量共用同一缓存目录与同一 key，双向命中复用」为已实施。实测目录读法不同源、委托路径无命中检查、ConvertRequest.node.updatedAt 是死字段（conversion-runner.ts 内 grep 零命中，实际失效维度是内容 hash）。现有测试无法捕获：conversion-runner.delegate.spec.ts 的 8 例从未断言缓存行为；两侧 spec 各自独立注入目录，没有一个测试断言两者同值。这是「ADR 声称已实施但未成立」，值得按 expand-contract 收尾票处理。
另一处必然 miss：SubmitConversionTaskDto.target（dto/conversion-task.dto.ts:22-30）只有 nodeId/version/format，无 width/height/colorPolicy/dwgVersion —— 异步预转换用默认值构造 key {hash}-pdf-2000x2000-mono，单文件下载带真实参数查 {hash}-pdf-3000x3000-color，#474 的「预转换→下载秒回」闭环只在默认 PDF 参数下成立。附带两个死参数：convertNodeForExport 的 priority 仅用于日志（:181）、ConvertRequest.node.updatedAt。

Problem
